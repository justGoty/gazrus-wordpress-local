# Подключение коллеги и инструкция другому чат-боту

Этот файл предназначен для коллеги с GitHub-логином `rozetka7-hash` и для чат-бота, который будет работать с проектом на другом компьютере.

## Текущее состояние проекта

- Репозиторий: `https://github.com/justGoty/gazrus-wordpress-local`.
- Рабочая ветка: `master`.
- WordPress-версия сохраняется как локальный прототип и источник контента.
- Новая версия проектируется как отдельный сайт-каталог без обязательной зависимости от WordPress.

- Контент первой версии обновляется через Codex и хранится в Git в структурированном виде.

## Как устроен Git в этом проекте

- Рабочая папка — локальные файлы на компьютере.
- `git status` показывает измененные, новые и удаленные файлы.
- Индекс, или staging, — только те файлы, которые войдут в следующий коммит.
- Коммит — зафиксированный логический набор изменений с понятным описанием.
- `origin/master` — состояние ветки `master` на GitHub.
- `git pull --ff-only` получает чужие изменения без автоматического merge-коммита.
- `git push` публикует локальные коммиты на GitHub.

В проекте разрешена работа напрямую через `master`, поэтому особенно важно синхронизироваться перед каждой задачей и не менять одновременно одни и те же файлы.

## 5. Обязательный цикл каждой задачи

### Перед работой

```powershell
git status --short --branch
```

Если рабочее дерево чистое:

```powershell
git fetch origin
git pull --ff-only origin master
```

Если `git status` уже показывает изменения, не выполнять `pull` и не удалять или откатывать их. Сначала определить владельца изменений, сохранить его работу и согласовать границы задачи.

В `WORKLOG.md` проверить последнюю выполненную работу. Задачу длительностью более 30 минут сначала забронировать через `docs/rebuild/ACTIVE_TASKS.md`: отдельный commit и push должны появиться в `origin/master` до начала изменения заявленных файлов.

### Во время работы

1. Менять только файлы текущей задачи.
2. Не перестраивать архитектуру без обновления документов в `docs/rebuild/`.
3. Не выдумывать характеристики, сертификаты, цены, наличие или статус дилера.
4. Для интерфейса проверять desktop и mobile в реальном браузере.
5. Для повторяющегося дефекта анимации упрощать или пересобирать эффект, а не ограничиваться проверкой синтаксиса.
6. Новые товары хранить в структурированных полях, пригодных для фильтрации.
7. Обновлять `WORKLOG.md`, когда закончена самостоятельная часть работы.

### Перед коммитом

```powershell
git status --short
git diff --check
git diff --stat
git diff
```

Добавлять только нужные файлы:

```powershell
git add -- path/to/file1 path/to/file2
git diff --cached --check
git diff --cached
```

Не использовать `git add .` без предварительной проверки состава файлов.

Коммит должен описывать один логический результат:

```powershell
git commit -m "Add stationary analyzer catalog filters"
```

### Перед отправкой

Другой участник мог успеть обновить `master`:

```powershell
git fetch origin
git rebase origin/master
```

После `rebase` повторить все проверки даже при отсутствии конфликта, затем отправить коммит:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check.ps1
git push origin master
```

Если возник конфликт:

1. Не выбирать автоматически только свою или только чужую версию.
2. Прочитать обе части и сохранить смысл обеих задач.
3. После исправления выполнить `git add -- <исправленные-файлы>`.
4. Продолжить `git rebase --continue`.
5. Повторно запустить проверки.

Никогда не использовать `git push --force` для `master`.

### Проверка публикации

```powershell
$local = git rev-parse HEAD
$remote = (git ls-remote origin refs/heads/master).Split("`t")[0]
"LOCAL=$local"
"REMOTE=$remote"
git status --short --branch
git show --name-status --oneline HEAD
```

`LOCAL` и `REMOTE` должны совпадать, а рабочее дерево должно быть чистым.

## 6. Координация двух исполнителей через master

- Перед началом сообщить второму исполнителю название задачи и файлы, которые планируется менять.
- Для задачи длительностью более 30 минут опубликовать бронь в `docs/rebuild/ACTIVE_TASKS.md`.
- Не работать одновременно над одним компонентом, документом или набором данных.
- Делить крупную работу на небольшие завершенные коммиты.
- После каждого `push` сообщать хеш коммита и результат проверки.
- Перед новой задачей снова выполнять `git pull --ff-only origin master`.
- Не оставлять в `master` заведомо сломанную промежуточную версию.
- Долгую работу делить на небольшие стабильные части; без отдельного решения владельца новые ветки не создавать.

## 7. Что нельзя публиковать

Нельзя коммитить:

- пароли и логины сервисов;
- SSH-ключи и серверные доступы;
- доступы к хостингу, домену, Dokploy, почте и админке;
- `.env` и локальные конфигурации с секретами;
- SQL-дампы и резервные копии;
- папки `backup/`, `db/`, `output/`;
- приватные медиа из `wp-content/uploads/`;
- архивы сайта и базы;
- персональные данные из заявок.

Перед публикацией выполнить узкую проверку новых файлов и staged diff. Если секрет уже попал в коммит, не продолжать публикацию и сразу сообщить владельцу: простого удаления в следующем коммите недостаточно.

## 8. Порядок разработки новой версии

1. Закрыть оставшиеся вопросы в `docs/rebuild/OWNER_QUESTIONNAIRE.md`.
2. Собрать перечень товаров, документов, фотографий и старых URL.
3. Утвердить единую модель данных и разные наборы фильтров для трех категорий.
4. Утвердить трехцветные дизайн-токены, типографику и прототипы основных страниц.
5. Создать новую основу приложения отдельно от WordPress-прототипа.
6. Реализовать каталог, поиск, фильтры, категории и карточку товара.
7. Реализовать форму КП с контекстом товара и отправкой на `info@prscom.ru`.
8. Реализовать калькулятор по проверенным формулам и нормативным источникам; СТА использовать только как функциональный референс.
9. Добавить реальные товары, документы, SEO-метаданные и карту редиректов.
10. Выполнить browser QA, тест доставки заявок, SEO-проверки и только затем переносить домен.

Сравнение моделей и отдельная CMS не должны задерживать MVP.

## 9. Инструкция чат-боту

Получив этот репозиторий, чат-бот должен:

1. Прочитать этот файл и документы из раздела «Текущее состояние проекта».
2. Проверить `git status --short --branch` и не перезаписывать существующие изменения.
3. Выполнить `git pull --ff-only origin master` перед началом задачи.
4. Проверить `docs/rebuild/ACTIVE_TASKS.md` и для длительной задачи опубликовать бронь отдельным commit+push.
5. Кратко сформулировать цель, ограничения и критерии приемки.
6. Проверить актуальный код и данные, а не исходить только из старых сообщений чата.
7. Реализовать задачу до рабочего состояния, включая тесты и визуальную проверку при изменении интерфейса.
8. Не копировать код, тексты и дизайн конкурентов. Допустимо изучать пользовательские сценарии и независимо реализовывать проверенную функциональность.
9. Не публиковать конфиденциальные файлы и данные.
10. Обновить документацию, `WORKLOG.md` и снять бронь активной задачи.
11. Сделать осмысленный коммит, выполнить проверки, синхронизироваться с `origin/master`, повторить проверки после `rebase`, отправить изменения и проверить совпадение локального и удаленного хешей.
12. В конце показать `git show --name-status HEAD`, чтобы состав опубликованного коммита был проверяемым.

## 10. Формат передачи результата

В конце задачи чат-бот сообщает:

```text
Сделано:
- ...

Проверено:
- ...

Не сделано / ограничения:
- ...

Следующий шаг:
- ...

Git:
- ветка master
- LOCAL=<полный локальный hash>
- REMOTE=<полный hash origin/master>
- MATCH=true
- рабочее дерево чистое: да/нет
```
