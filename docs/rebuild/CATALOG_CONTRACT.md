# Контракт товарного каталога

Статус: рабочий контракт MVP от 3 августа 2026 года. Меняется только вместе со схемой в коде, миграцией данных и обновлением этого документа.

## Владение данными

| Данные | Источник истины |
|---|---|
| Товары, справочники, SEO и redirects | Git, `web/content/catalog/` |
| Схема и проверки | Код приложения, `web/src/lib/catalog/` |
| Изображения и PDF в production | S3-совместимое хранилище; в Git только публичные тестовые ассеты малого размера |
| Заявки и статусы доставки | PostgreSQL |
| Пароли, SMTP, БД и S3-доступы | Dokploy environment, никогда не Git |

Поисковый индекс всегда строится из каталога того же Git SHA, что и приложение.

## Структура

```text
web/content/catalog/
  products/*.json
  dictionaries/gases.json
  dictionaries/brands.json
  redirects.json
```

Один товар хранится в одном JSON-файле. Другой формат или параллельный источник без отдельного решения не вводится.

## Обязательные поля товара

- `schemaVersion`: версия контракта.
- `id`: неизменяемый UUID, не зависит от URL и модели.
- `slug`: уникальный человекочитаемый URL в нижнем регистре.
- `status`: `draft`, `published` или `archived`.
- `category`: `stationary`, `portable` или `sensors`.
- `brandId`, `model`, `title`, `summary`.
- `commercialMode`: только `request_quote`.
- `gases`: ссылки на справочник газов.
- `ranges`: массив диапазонов измерений.
- `highlights`: до шести ключевых пар «параметр — значение» для карточки каталога.
- `specifications`, `applications`, `modifications`: подробные данные страницы товара; пустые массивы допустимы.
- `documents`, `media`, `seo`, `sources`.
- `updatedAt` в ISO 8601; `verifiedAt` обязателен для `published` и отсутствует у непроверенного черновика.

Диапазон хранится атомарно:

```json
{
  "gasId": "co",
  "min": 0,
  "max": 100,
  "unit": "ppm",
  "resolution": 1,
  "conditions": "при условиях из паспорта"
}
```

Текстовое поле не заменяет характеристику, которая участвует в фильтре. Значения `min`, `max` и `resolution` являются числами, единицы берутся из закрытого справочника.

## Проверка записи

1. JSON проходит схему Zod/JSON Schema.
2. `id` и `slug` уникальны во всем каталоге.
3. `min < max`, газ и единица существуют в справочниках.
4. Для `published` заполнены P0-поля категории, изображение, источник и дата проверки.
5. Документы и медиа имеют проверяемые URL, тип и понятное описание.
6. SEO title/description не дублируются механически между товарами.
7. Старый URL либо совпадает с новым, либо присутствует в `redirects.json` один раз.

Тематические изображения категорий могут быть новыми композициями на основе референсов. Основное изображение конкретного товара обязано сохранять фактическую конструкцию модели; допустимы кадрирование, выравнивание фона, экспозиции и цвета, но не генеративная замена деталей.

Запись с непроверенной характеристикой остается `draft`. Пропуски не заполняются догадками.

## Порядок добавления через Codex

Полный рабочий регламент: [PRODUCT_CREATION_STANDARD.md](PRODUCT_CREATION_STANDARD.md).

1. Приложить паспорт, руководство или официальный источник производителя.
2. Создать или обновить одну товарную запись и указать источник каждого спорного значения.
3. Запустить проверку схемы, lint и production build.
4. Показать diff ответственному за контент.
5. После проверки перевести товар в `published`, сделать commit и push.

Конвертеры импорта создают отчет об ошибках и не публикуют частично разобранную запись автоматически.
