# Техническая архитектура

Статус: обновлено по подтвержденным решениям владельца 3 августа 2026 года.

## Сравнение

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| Next.js и структурированные данные в Git | Прозрачные изменения, review и удобное наполнение через Codex | Менеджер зависит от разработки | Рекомендуется для MVP |
| Next.js + headless CMS | SSR, структурированные данные, удобная админка | Нужны БД, миграции и backup | Добавить при самостоятельном наполнении |
| Next.js + WordPress как CMS | Можно быстрее забрать текущий контент | Остаются две системы и WordPress | Запасной путь миграции |

## Рекомендуемый стек

- Next.js App Router и TypeScript.
- Версионируемые YAML/JSON-файлы товаров с проверяемой схемой.
- PostgreSQL для журнала заявок и статусов доставки.
- Docker и Dokploy.
- S3-совместимое хранилище для изображений и документов.
- Поисковый индекс, собираемый из версионируемых данных каталога; отдельный поисковый сервис добавляется только после замера фактического объема.
- Яндекс Метрика и серверный журнал заявок.

Текущая основа в `web/` фиксирует Node.js 22, pnpm 11.9.0, Next.js 16.2.12, React 19.2.4, TypeScript 5.9.3 и Zod 4.4.3. Обновление выполняется отдельной задачей после проверки сборки и browser QA.

Официальные документы подтверждают self-hosting Next.js в Node/Docker и работу ISR. Payload остается проверенным вариантом будущей админки, но не входит в обязательный MVP:

- [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting)
- [Next.js ISR](https://nextjs.org/docs/app/guides/incremental-static-regeneration)
- [Payload Admin Panel](https://payloadcms.com/docs/admin/overview)
- [Payload Collections](https://payloadcms.com/docs/configuration/collections)
- [Payload PostgreSQL](https://payloadcms.com/docs/database/postgres)

## Модель данных

Основные сущности контента и каталога:

- Products.
- Categories.
- Gases.
- Brands.
- SensorTypes.
- Applications.
- Industries.
- Services.
- Documents.
- Pages.
- Redirects.
- Users добавляются только вместе с CMS.

Операционные `Leads`, `LeadItems`, `EmailOutbox` и `DeliveryAttempts` хранятся в PostgreSQL и не входят в Git-каталог.

Структурированные поля товара:

- тип и назначение;
- бренд, модель, артикул и статус;
- контролируемые газы;
- массив диапазонов: газ, минимум, максимум, единица, разрешение;
- технология сенсора и способ отбора;
- число каналов;
- время отклика;
- IP, Ex и температура эксплуатации;
- выходы, интерфейсы, питание и реле;
- поверка, межповерочный интервал и Госреестр СИ;
- изображения, схема, документы, комплектация и аксессуары;
- коммерческий статус `request_quote`, наличие и срок поставки;
- SEO, старые URL и связанные товары.

Свободный текст не должен заменять поля, используемые в фильтрах.

## Публикация контента через Codex

1. Для товара фиксируется исходный паспорт, руководство, официальный сайт производителя или другая проверяемая первичная основа.
2. Codex переносит данные в структурированные поля, не заполняя пробелы догадками.
3. Схема проверяет обязательные поля, единицы, справочники и уникальность модели.
4. Второй человек или назначенный владелец данных сверяет ключевые характеристики и документы.
5. Изменение проходит diff, commit и push; источник и дата проверки остаются рядом с записью товара.
6. Публикация выполняется только после успешной сборки и проверок каталога.

Ответственный за товарные данные и минимальный процент заполненности P0-полей остаются открытыми решениями владельца.

## Каталог и поиск

- Все фильтры работают на сервере и сохраняются в URL.
- Кнопки назад/вперед восстанавливают состояние.
- Поиск понимает модель, артикул, бренд, газ и русские варианты написания.
- Meilisearch добавляется только при доказанной необходимости.
- Индексируемые посадочные создаются отдельно от случайных комбинаций фильтров.
- Сравнение не входит в обязательный MVP и не усложняет первую модель состояния каталога.

## Заявки

Форма передает:

- товары и количество;
- газ, задачу и условия;
- выбранные фильтры;
- требования к поверке и документам;
- контакт, UTM, источник и согласие.

На сервере:

1. Валидация, honeypot и rate limit.
2. Запись заявки в PostgreSQL.
3. Асинхронная отправка основного письма на `info@prscom.ru` с повторными попытками.
4. Интеграция с CRM добавляется позднее без изменения формы.
5. Статус доставки и журнал ошибки.

## Развертывание

- Reverse proxy перед Next.js.
- Для MVP используется один экземпляр Next.js; при горизонтальном масштабировании кэш и фоновые задачи выносятся в общие сервисы.
- Отдельные контейнеры приложения и PostgreSQL.
- Постоянные volumes только для БД; медиа вне контейнера.
- Автоматический backup БД и проверка восстановления.
- Staging закрыт от индексации.
- Секреты хранятся в Dokploy environment, не в Git.
- Healthcheck, журнал ошибок и план отката.
- HTTP healthcheck новой версии: `/api/health`; переменная `APP_REVISION` содержит Git SHA развернутого образа.

Пайплайн публикации:

1. Push в `master` запускает проверку ссылок документации, схемы каталога, lint, тесты и production build.
2. Образ приложения маркируется полным Git SHA, из которого он собран.
3. Этот же образ проходит smoke-проверку на staging.
4. В production продвигается уже проверенный образ без повторной сборки.
5. Откат выполняется на предыдущий известный Git SHA и образ.

Поисковый индекс собирается из того же набора товарных данных и Git SHA, что и приложение. Это исключает расхождение карточки, фильтров и результатов поиска.

## Миграция

1. Заморозить WordPress как источник.
2. Экспортировать товары, таксономии, документы и legacy URL.
3. Нормализовать характеристики.
4. Импортировать в структурированный каталог с отчетом об ошибках.
5. Сопоставить старые и новые URL.
6. Проверить staging.
7. Переключить домен и оставить WordPress-архив недоступным для индексации.

## Тесты

- Unit: конвертер, нормализация диапазонов, фильтры.
- Integration: импорт, поиск, формы, журнал заявок и отправка почты.
- Browser: каталог, фильтры, КП, calculator и redirects.
- Visual: desktop/mobile, все сцены и reduced motion.
- SEO: status, title, canonical, robots, sitemap и JSON-LD.

Граница расчетного ядра, справочник и контрольные проверки определены в [CALCULATOR_SPEC.md](CALCULATOR_SPEC.md).
Формат товарных записей определен в [CATALOG_CONTRACT.md](CATALOG_CONTRACT.md), доставка заявок — в [LEAD_DELIVERY.md](LEAD_DELIVERY.md).

## Риски

- Неполные или противоречивые характеристики.
- Неясная разница между портативными и переносными.
- Неподтвержденные нормативы калькулятора.
- Потеря трафика без полной URL-карты.
- Рост сложности, если онлайн-оплата или 1С внезапно войдут в MVP.
